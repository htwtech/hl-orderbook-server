# Согласованность книги: расследование, исправления, где остановились

Сентябрь 2026, форк `htwtech/hl-orderbook-server`, ветка `fix/diff-before-status`
(слита в `main` и `l2diff`, `fd8b973`). Документ для того, кто будет менять этот
код дальше: что именно ломалось, как это находили, почему решения такие, а не
другие, чем проверять, и что осталось открытым. Числа — измеренные, с датами;
предположения помечены.

Устройство сервера в двух словах, чтобы дальше было понятно. Нода пишет три
потока файлов, по одному файлу в час: `node_order_statuses_streaming`
(статусы ордеров: `open`, `filled`, `canceled`…, ~19,7 млн строк/час, 10,8 ГБ),
`node_raw_book_diffs_streaming` (изменения книги: `New`, `Update`, `Remove`,
~11,6 млн строк/час, 2,9 ГБ) и `node_fills_streaming`. Строка — `Batch` с
`block_number`, `block_time` и списком событий. ~14 блоков/с, ~677 строк
статусов и ~400 строк диффов на блок. Сервер собирает L4-книгу: ордер
попадает в книгу, когда встречаются его `open`-статус (в нём сторона, цена,
размер) и `New`-дифф (в нём размер и позиция в очереди уровня); до встречи
половинки лежат в кэшах ожидания `pending_order_statuses` /
`pending_new_diffs`. `Update`/`Remove` применяются к книге. L2 (`l2Book`) —
агрегат L4 по уровням, пересчитывается из книги при каждом флаше. Стартовое
состояние — снимок `hl-node compute-l4-snapshots` из сохранённого состояния
ноды `abci_state.rmp`.

---

## 1. Симптом

Два сервера (A и B) на одной машине, каждый на своей ноде (`hyperliquid1`,
`hyperliquid2`), одинаковый код — и **разные** L2-книги для BTC. Заметили
через wsarb, который держит оба как источники: у одного лишние уровни, у
другого недостающие, уходило и приходило само.

Первая гипотеза — ноды пишут разное. Проверили `tools/node-files-compare.py`:
часовые файлы статусов и диффов у двух нод **идентичны байт в байт**. Значит,
одинаковый код на одинаковых входных данных даёт разный результат — разница
только во *времени* чтения. Дальше искали только в сервере.

## 2. Инструменты (все в `tools/`, Python, без зависимостей кроме `websockets`)

| инструмент | что делает | что показал |
|---|---|---|
| `node-files-compare.py` | сравнивает часовые файлы двух нод | файлы идентичны → проблема в сервере |
| `l2-vs-api.py --ours A B --coin BTC --seconds N [-v]` | наш `l2Book` с A и B против публичного API, кадры сопоставляются **по времени блока**; считает идентичные кадры, «полы» (floors) и куда смещено «shows more» | полы — главный признак: уровень, где разница в размере/числе ордеров держится 3 кадра подряд, это либо лишний ордер (фантом), либо недостающий |
| `diff-orphans.py --data-dir … [--hours N]` | классифицирует `Remove`/`Update`, которым в диффах не предшествует `New` | 56 % — только `canceled`, 39 % — `Update(0)` затем `Remove` (полное исполнение) |
| `diff-orphans.py --oids FILE --hours N` | по списку oid (голые числа или строки лога `oid=N`) поднимает всю историю из файлов ноды: диффы, статусы, вердикт | так нашли протокольный адрес и «open→filled в одном блоке» |
| `l4-phantoms.py --a http://…:48001 --b http://…:48002 --coin BTC --seconds N` | раз в секунду `GET /l4Book` у обоих в полосе ±0,3 % вокруг мида, сравнение **по oid**; докладывает то, что держится 3 опроса; **первая строка-пульс — вся книга без полосы** | именно им доказано, что после исправления две книги совпадают ордер в ордер (60 998 = 60 998) |

Про `l2-vs-api.py`: строки `no frame at this time` — артефакт: наши кадры
режутся по таймеру (50 мс) и не на каждое время блока приходится кадр; 2–3
неидентичных кадра из 40 без полов — кадр снят посреди применения блока
(одна сторона отдала кадр с половиной блока), это не расхождение книг.
Полы — единственная метрика, которая отделяет книгу от момента снятия.

Журнал и метрики. Журнал сервера в UTC (как и `date` на сервере, но `date`
печатает 12-часовой формат). **Проверяйте дату сервера** перед `--since`: один
раз запрос ушёл на завтрашнюю дату, и обе «пустые» выборки ничего не значили.
Файлы ноды хранятся несколько часов: трассировку `--oids` делать сразу после
поимки. Читаемый фильтр журнала:

```sh
journalctl -u hyperliquid-ws --since "2026-09-16 09:00" --no-pager \
  | grep -E "WARN|ERROR" | grep -vE "pending_order_statuses|insertBefore" \
  | sed -E 's/^.*\]: //; s/[0-9]+/N/g' | sort | uniq -c | sort -rn | head
curl -s localhost:9090/metrics | grep -E "desyncs_total|pending_new_evicted|diff_without_order|skew_gate_held|stream_skew"
```

## 3. Причины, в порядке обнаружения

Каждая — отдельный механизм, и каждая по отдельности давала расхождения.
Пока не была закрыта последняя, картина не сходилась целиком, поэтому ниже
у каждой — что именно она объясняла и что нет.

### 3.1. Гонка `New → Remove → open` — фантом на каждом быстро снятом ордере

`29905d6`, `02da54f`, `e151cfb`.

Потоки читают независимые потоки, дифф-поток обычно впереди (файл статусов в
несколько раз больше). Ордер ставится и тут же снимается: в диффах `New`,
потом `Remove`; `Remove` не находит ордера в книге (он ещё ждёт статус) и
молча пропадает; приходит `open` — ордер вставляется в книгу и **остаётся
навсегда**. Никто не считал это потерей.

Исправление: `Update`/`Remove`, не нашедшие ордера в книге, применяются к
ожидающему `New` (`apply_diff_to_pending_new`): размер меняется или запись
удаляется. Отдельно `Update(newSz=0)` + `Remove` — так нода пишет полное
исполнение; `Update(0)` убирает ордер, следующий `Remove` — ожидаемый промах
(`after_zero`, окно 64 блока). Метрика
`orderbook_diff_without_order_total{kind,outcome}`:
`pending_dropped`/`pending_updated` — гонка поймана; `after_zero` — полное
исполнение; `unknown` — ордер, которого сервер не видел вовсе (см. §5).

### 3.2. Кэши ожидания чистились целиком — двигатель цикла пересборок

`b6bb4d7`.

Пороги `MAX_PENDING_*` (200 000) при переполнении **обнуляли кэш целиком**.
После каждой пересборки читатели догоняли файлы неравными кусками, дифф-поток
уходил на тысячи блоков вперёд, `pending_new_diffs` переполнялся, чистился —
~10 000 `New` в секунду терялись, несколько секунд подряд; каждый потерянный
`New` — недостающий ордер; их обнаружение позже — «data loss» — новая
пересборка. Цикл в 6–10 минут, в журнале 38 пересборок за два часа.

Исправление: пороги — только защита памяти; при переполнении уходит самое
старое (по `Instant`), считается потерей. Настоящее лечение — §3.3.

### 3.3. Порядок применения потоков — четыре версии, три неудачные

`1007bbb`, `3f0238c` (шлюз по skew), `9a95907` (`StreamMerge`), `47102b5`
(`LiveMerge`, итог).

Задача: два потока должны применяться в порядке блоков, статус раньше диффа
того же блока — так нода их и породила. Что пробовали:

1. Шлюз в слушателе, держит поток, ушедший вперёд, 2 с → качели, skew −129
   блоков.
2. Шлюз с освобождением по счётчику доставок → skew −1591, 200 000 строк в
   удержании, статусы за порогом кэша.
3. `StreamMerge` — очереди в слушателе, слияние по высоте → при догоне skew
   −2400: у очередей нет обратного давления, читатели заливают их кусками
   разного размера.
4. **`LiveMerge`** — у каждого книжного потока свой ограниченный канал
   (`LIVE_STREAM_LINES = 20 000`), слушатель берёт того, у кого в голове
   меньший блок, статус раньше диффа; поток, ушедший вперёд, упирается в
   свой канал и ждёт. Одинокий поток (у другого канал пуст) применяется до
   32 блоков за последнюю взятую высоту другого (`MERGE_LOOKAHEAD_BLOCKS`),
   дальше ждёт; если другой не отдаёт ничего 10 с, пока его ждут
   (`MERGE_DEAD_WAIT`), он мёртв — это случай сторожа, книга идёт за живым.
   Память ограничена каналами, skew в работе — 0.

Урок: обратное давление должно быть там, где читают, а не там, где
применяют; любые «освобождения» по таймеру или по счёту срабатывают именно
при догоне и отпускают всё сразу.

Метрики: `orderbook_stream_skew_blocks` (статусы минус диффы),
`orderbook_skew_gate_held` (строк в двух каналах).

### 3.4. Старт: снимок раньше окончания backfill, читатели «в живую» с разницей в backfill

`67690bf`.

Установка снимка забирала кэш replay, а строки backfill, пришедшие позже,
выбрасывались (`late_backfill`, 221 934 строки на одном старте). И читатель,
закончивший backfill первым, уходил в живой режим на целый backfill раньше
другого — половинки старели раньше, чем читалась вторая. Исправление: первый
снимок после обоих backfill, живой режим начинают вместе. (Первая половина
позже переделана в §3.7, вторая осталась.)

### 3.5. Ордера протокольного адреса — «потеря данных» каждые 6 минут

`831148f`.

После §3.1–3.4 A прожил 14 минут без единой пометки, но пересборки остались,
раз в ~6 минут, всегда по одной причине: «Evicted N aged pending_new_diffs
(status never arrived — data loss)». Трассировка `--oids` 16 из 16: адрес
`0xffffffffffffffffffffffffffffffffffffffff`, только спотовые пары, `New`
есть, статуса **нет вообще**, `Remove` тоже нет. Нода не пишет статусы для
собственных ордеров протокола, а без статуса нет стороны — вставить нельзя.
Их `New` 60 с ждал, выселялся как потеря, книга пересобиралась целиком.

Исправление: `pending_new_diffs` хранит адрес владельца; при выселении по
возрасту протокольные считаются отдельно
(`orderbook_pending_new_evicted_total{owner="protocol"}`, `info`), не
потеря; любые другие — потеря (`owner="other"`, должно быть 0). Следствие,
задокументировано в README: на споте у нас нет ордеров `0xff…ff`, которые
публичный API, вероятно, показывает. Перпы не затронуты.

### 3.6. Что оказалось нормой (и чем шумит журнал)

- `Evicted N aged pending_order_statuses` — `open`-статус, к которому за 60 с
  не пришёл `New`. Трассировка 2 507 таких за 10 минут: в выборке все до
  одного — `open@h → filled@h` в одном блоке, диффов нет. Нода не пишет дифф
  для ордера, который не пролежал в книге ни блока (исполнен при постановке,
  `FrontendMarket`, триггерные). Не потеря; переведено в `debug` (`fd8b973`).
- `insertBefore anchor … missing; rested at back of level` — `New` с якорем
  (ALO-ордер встаёт перед конкретным oid), а якоря нет: он в ожидании статуса
  (дифф-поток впереди в пределах 32 блоков) или уже снят. Страдает только
  очередь внутри уровня, не состав книги. У B их было в 4 раза больше, чем у
  A (4 138 против 1 048 на BTC за 90 минут) — потому что у B дифф-поток
  чаще впереди статусов; это не ошибка книги, но индикатор skew.
- `diff_without_order{outcome="after_zero"}` — полное исполнение, норма.

### 3.7. Главная: дыра между сохранённым состоянием ноды и головой

`36be1a0`. Найдена последней, объясняет всё, что оставалось.

**Как проявлялась.** После §3.1–3.5 оба сервера жили часами без пересборок и
предупреждений, но `l4-phantoms.py` показал: у A 87 асков, которых нет у B,
у B 98 асков, которых нет у A, по всей книге 511/833 ордеров; все — с первого
опроса, все — аски в 75 911–76 108; в 23:30:05 обе группы исчезли **разом**
(цена прошла через полосу) — и ни один сервер не пересобирался. Разные
владельцы, много — не отмена. Ключ: в книге сервера есть **локальный
матчинг** (`OrderBook::add_order_before` → `match_order`): вставляемый ордер,
пересекающий противоположную сторону, «съедает» встречные ордера в книге.
Поэтому лишний ордер (чей `Remove` сервер не видел) живёт до первого прохода
цены — и исчезает, заодно уменьшив размер тому, кто его «исполнил». Значит,
расхождения были **со старта каждого сервера** (A 21:40, B 22:23 UTC 15.09),
далеко от мида, и вымывались только там, где проходила цена. Все «полы» B в
22:57, которые «появлялись и исчезали», были тем же: цена подходила к
постоянным фантомам и уходила.

**Механизм.** Снимок считается из `hyperliquid_data/abci_state.rmp` —
состояния, которое нода **сохраняет каждые 10 000 блоков** (~12 минут; высоты
кратны 10 000, mtime файла подтверждает период). Высота же бралась из
`visor_abci_state.json`, а этот файл ведёт **голову** — обновляется каждый
блок, отстаёт от книги на ~3 с (измерено `stat`/`cat` раз в 30 с). Три
следствия в коде до исправления:

1. пол backfill = голова → из файлов не читалось ничего ниже неё;
2. отсечка replay = голова → всё в кэше ниже неё выброшено как «уже в снимке»;
3. кэш replay начинает копиться с начала fetch — события до него в кэше нет.

Дыра `(H_rmp, голова]` — от 0 до 10 000 блоков на **каждой** установке
снимка: `New` из неё — недостающие ордера, `Remove` из неё — лишние. Старый
код пересобирался каждые 6 минут (§3.5) и засевал такую дыру каждый раз —
вот откуда «фантомы при одинаковых файлах». Автор кода считал, что
`visor_abci_state.json` хранит высоту сохранённого состояния (комментарии в
коде это говорят прямо); на нашей ноде это не так.

Высота сохранённого состояния лежит в первых байтах rmp: MessagePack, карта
`exchange → locus → ctx → {height, time}`; `head -c 256 | xxd` показал
`a6 "height" ce 44 84 21 70` = 1 149 510 000 и `time = 2026-09-16T08:36:42`.

**Исправление.**

- `utils::read_abci_state_height` — минимальный разборщик MessagePack (карты,
  строки, целые, пропуск любого значения), читает первые 64 КБ, идёт по
  ключам; `persisted_height` — она же с запасным вариантом «visor + громкий
  `warn`, что дыра открыта». Тесты на реальном заголовке (146 байт с диска),
  обрезанном заголовке, чужих ключах и пропуске всех типов.
- Пол backfill и отсечка replay = высота rmp.
- 12 минут потока — ~6 млн строк; копить их разобранными в кэше replay
  (порог 4 млн событий) нельзя. Backfill теперь идёт **в те же ограниченные
  каналы, что живые строки**, впереди них; слушатель не берёт из merge
  (`merge_active = false`), пока снимок не установлен — читатели просто
  стоят на полных каналах, строки лежат на диске. После установки merge
  применяет всё в порядке блоков, а то, что ≤ высоты снимка (нода успела
  сохраниться во время дампа), отбрасывает по высоте (`LiveMerge.floor`).
  Кэш replay остался в коде, но в этих сценариях пуст.
- Пересборка — тот же путь: читатели **перезапускаются** с высоты rmp
  (старые выходят сами, когда их каналы закрыты), книга стоит, пока не
  установится новый снимок, потом догоняет. До этого пересборка тоже несла
  дыру: события `(H_rmp, начало fetch]` были применены к старой книге и в
  кэше их не было.
- Снятие пометки потери: раньше сравнивалось с высотой снимка; теперь с
  головой на момент старта установки (`install_covers`), иначе с высотой rmp
  (ниже головы до 10 000 блоков) каждая пересборка тянула бы следующую.
- Предупреждение о повторной вставке oid — с выборкой 1/1000: при
  переигрывании поверх более свежего снимка их тысячи, и это ожидаемо.

**Проверка.** B, старт 09:13:04 UTC 16.09: `Persisted state … 508 blocks
behind the head` → снимок установлен 09:13:21 → за 6 с прочитано и применено
349 975 диффов + 569 808 статусов (то, что раньше выбрасывалось) → живой
режим. A, 09:27: дыра 2 387 блоков, 2,47 млн + 3,44 млн строк за 40 с
(~150 000 строк/с). Первая строка `l4-phantoms.py` по всей книге на одной
высоте: **60 998 = 60 998, A only 0, B only 0, differ 0**. Против API за 5
минут: полов 0 у всех пар, идентичных кадров 91–95 %. Через час: журналы
без единого `WARN`/`ERROR` (кроме двух классов из §3.6), `desyncs_total`
отсутствует, `pending_new_evicted{owner="other"}` отсутствует, skew 0.

## 4. Что осталось как есть — известные ограничения

- **После установки снимка книга отстаёт** на размер дыры (до ~12 минут) и
  догоняет со скоростью ~150 000 строк/с — минута-две в худшем случае.
  `is_ready` этого не ждёт: клиенты получают кадры со старым `time`. wsarb
  отсекает по `--max-age`; другим потребителям смотреть на `time`. Идея на
  потом: не отдавать `ready`, пока высота книги не в ~200 блоках от visor.
- **Пересборка останавливает книгу** на время дампа + сборки (~15–30 с).
  Раньше старая книга продолжала обновляться — но она в этот момент по
  определению неверна, а простота важнее.
- **Очередь внутри уровня** может быть неточной, когда дифф-поток впереди
  статусов в пределах 32 блоков (`insertBefore` fallback). На L2 не влияет.
- **Спот без ордеров `0xff…ff`** (§3.5).
- **Fills не backfill'ятся** — сделки из дыры/стартового окна теряются;
  книга не затронута.
- **Кадры L2 режутся по таймеру** и могут быть сняты посреди применения
  блока — 2–3 кадра из 40 расходятся с другим сервером на 1–3 уровня.
  Возможное улучшение: флаш только на границе блока.
- `diff_without_order{kind="remove",outcome="unknown"}` растёт (A: 183 227
  за 10,5 ч на старом коде). Часть — `Remove` для протокольных ордеров после
  их выселения, часть — из стартовой дыры. **На новом коде темп роста не
  перемерен.** Если он заметен после чистого старта — трассировать oid из
  `sample 1/1000` в журнале (`diff without order … unknown`).
- Стартовый backfill читает часовой файл линейно с начала (до 10 ГБ) и
  фильтрует по высоте — это секунды, но при желании можно искать позицию
  бинарным поиском по смещению.
- `--no-resync` (`tolerate_drift`) — из исходного проекта, не наша опция.
